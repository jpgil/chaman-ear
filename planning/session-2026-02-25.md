## Introspección de la Sesión

### TL;DR
Completada exitosamente la conceptualización de Chaman-ear. Se produjo la arquitectura base, especificaciones técnicas completas y un roadmap de ejecución en 6 fases. Destaca la decisión clave de usar texto parcial inteligente directamente desde Gemini.

### Cadena de decisiones
1. **Flujo Stateless**: Se prefirió enviar el contexto en cada WS Connect para mantener el servidor simple y proxy puro.
2. **Completitud Inteligente**: Decidimos que Gemini se encargue de "limpiar y completar" la idea en tiempo real en los eventos `partial`.
3. **Runtime Backend**: Tras la revisión final del PM, se decidió usar **Python (FastAPI)** como tecnología base para el servidor. Esta decisión viene por motivos estratégicos externos a este repositorio. Las specs deberán ajustarse levemente durante la Fase 1 para acomodar esta decisión final (Python en lugar de Node.js).
4. **Fase de Investigación Previa**: Se agregó la Fase 0 al Plan de Ejecución para no construir a ciegas.

### Micro-decisiones clave
| Decisión | Contexto | Impacto |
|----------|----------|---------|
| Prompt Externo | Necesidad de iterar rápido el sistema de inteligencia | El prompt vivirá en un `.txt` separado del código. |
| default `formatInstruction` | Facilitar el uso on-the-go del SDK | Si el usuario no lo define, un comportamiento "limpio por defecto" estará seguro. |
| Test-Driven Development | Requerimiento de desarrollo estable | Todas las tareas de ejecución de las Fases se desglosaron en criterios TDD (*RED -> GREEN -> REFACTOR*). |

### Sorpresas
* Anticipábamos una especificación general en este inicio, pero descubrimos que la inteligencia crítica ocurre definiendo a fondo las instrucciones (Completitud Inteligente). No habrá post-procesamiento local.
* Gemini ya usa WebSockets por lo que utilizar SSE o APIs REST en nuestro backend habría sido contraproducente.

### Aprendizajes
1. **La clarificación del flujo parcial es crítica**: Al documentar explícitamente qué esperamos en un fragmento de voz "a medias", solidificamos todo el producto. Los ejemplos en el brief sentaron el estándar de éxito para todo el desarrollo.
2. **Python vs TS para el backend**: El backend FastAPI requerirá un enfoque levemente diferente durante la configuración del monorepo en comparación con un mono-ecosistema en TS, pero es la mejor decisión estratégica.
